# 維護 wiki 知識庫

所有步驟都靠 `kb` 指令。`kb` 的輸出會告訴你下一步做什麼，**照輸出的「下一步」做**。

## 開始前：確認 kb 指令可以用

先執行 `kb --help`。

- 有列出指令說明：可以用，繼續下面的步驟。
- 出現「找不到指令」之類的錯誤：這台電腦還沒安裝 LLM Wiki 工具（`kb` 指令與 wiki MCP 是同一套）。**不要自己安裝，也不要改用其他方法**，把下面這段話告訴使用者，等使用者說裝好了再繼續：

  > 這台電腦還沒安裝 LLM Wiki 工具。請到以下路徑取得，並依該資料夾 README 的「安裝」與「設定 wiki MCP」完成安裝：
  >
  > `//fileserver/share/tools/llm-wiki`（範例路徑，請換成實際位置）
  >
  > 裝好後 `kb` 指令與 wiki MCP 都可以使用，請告訴我繼續。

使用者說裝好之後，再執行一次 `kb --help` 確認。

## 規則

- 你只能新增或修改 `wiki/` 裡的頁面檔。
- 不要修改 `index.md`、`log.md`、`.kb/`、`raw/`。這些由 `kb` 指令處理。
- 不要自己執行 `git` 指令。
- 不知道的欄位去問使用者，不要自己編。
- 只寫來源裡有的內容。

## 建立新的知識庫

1. 向使用者問這六項：代號（name）、名稱（title）、一句話描述（description）、擁有者（owner）、分類（category）、機密等級（confidentiality，只能是 `public`、`internal`、`confidential` 其中之一）。
2. 執行：

   ```
   kb init <資料夾> --name <代號> --title "<名稱>" --description "<描述>" --owner <擁有者> --category <分類> --confidentiality <機密等級>
   ```

3. 照輸出的「下一步」做。

## 整理來源的工作方式（先讀這一節）

**品質優先於速度。** 不要為了快而一次處理多份、合併步驟、或跳過檢查。

整理來源時有三種角色。你收到的任務訊息開頭寫「你是作者」或「你是檢查者」時，你就是那個角色，只做那個角色的事，**不要再派工**。其他情況你是派工者。

| 角色 | 做什麼 | 不做什麼 |
| --- | --- | --- |
| 派工者 | 排順序、一次派一份、收回報、最後總結 | 不讀來源內容、不寫頁面、不改頁面 |
| 作者 | 處理**一份**來源，做到 `kb ingest commit` 成功 | 不處理第二份來源 |
| 檢查者 | 對照來源原文檢查作者剛寫的頁面，補檢索測試 | 不新增來源沒有的內容 |

為什麼這樣分：

- **一份來源用一個新的 subagent。** 對話越長，寫出來的頁面品質越差、速度也越慢。每份來源都從乾淨的狀態開始。
- **依序處理，不同時進行。** 同一個知識庫一次只能處理一份來源，同時開始第二份會被 `kb` 擋下。而且後處理的要看得到先處理的頁面，才能把內容併進既有頁面，不會寫出重複的頁面。
- **作者不檢查自己寫的頁面。** 寫的人會照自己的印象讀，看不出錯。換一個沒讀過來源的人，對照原文才看得出來。
- **派工者不讀來源。** 派工者從頭做到尾，沒辦法換成乾淨的狀態，所以只留簡短的回報。

### 派工者的步驟

在知識庫資料夾內執行。

1. 執行 `kb ingest start`，取得待處理的來源清單。清單開頭說有來源「正在處理」時，那是上次沒做完留下的：執行 `kb ingest abort` 清掉，再重新列一次。
2. 排順序，把順序列給使用者確認後再開始：
   - 概觀、規格這類文件排前面，程式碼排後面。
   - 檔名相近、看起來在講同一個東西的排在相鄰。
3. 照順序，**一次只派一份**。每一份做兩件事：
   1. 開一個新的 subagent 當作者，任務訊息用下面的「給作者的任務」。等它回報。
   2. 作者回報成功後，開**另一個**新的 subagent 當檢查者，任務訊息用下面的「給檢查者的任務」。等它回報。
4. 作者回報失敗時，執行 `kb ingest status`。還顯示「正在處理」就執行 `kb ingest abort`。記下這份來源與失敗原因，繼續下一份，不要自己接手寫頁面。
5. 每處理完 5 份來源，執行一次 `kb lint`。有 `[錯誤]` 就開一個新的 subagent，把 `kb lint` 的輸出交給它，照「檢查知識庫（lint）」一節修正。
6. 全部處理完後，執行 `kb lint`，然後向使用者總結：處理了幾份、各新增與修改了哪些頁面、檢查者修正了什麼、哪些來源失敗與原因。

只有一份來源待處理時，作者的工作可以自己做，但檢查仍然要派給另一個 subagent。

目前的環境不能開 subagent 時：自己照「處理一份來源的步驟」依序做，每份做完就 commit。處理超過兩份後，告訴使用者「建議開新的對話繼續，品質會比較好」，由使用者決定。

**給作者的任務**（把 `<…>` 換成實際內容，其餘原樣交給 subagent）：

> 你是作者。知識庫在 `<知識庫資料夾>`。請用 wiki-maintain skill 的「處理一份來源的步驟」處理這一份來源：`<來源檔>`。
> 只處理這一份，做到 `kb ingest commit` 顯示「ingest 完成」。不要處理其他來源，不要再派工。
> `kb ingest start` 的第一行會顯示來源「共 N 行」。超過 5000 行時，先不要寫頁面：執行 `kb ingest abort`，回報「來源太長」。
> `kb ingest commit` 連續 3 次沒通過時，執行 `kb ingest abort`，回報失敗與最後一次的錯誤訊息。
> 完成後只回報這幾項：來源檔、新增的頁面代號、修改的頁面代號、成功或失敗、沒解決的問題。

**給檢查者的任務**：

> 你是檢查者。知識庫在 `<知識庫資料夾>`。作者剛處理完來源 `<來源檔>`，新增或修改了這些頁面：`<頁面代號清單>`。
> 請用 wiki-maintain skill 的「檢查者的步驟」檢查這些頁面。不要處理其他來源，不要再派工。
> 完成後只回報這幾項：檢查了哪些頁面、修正了什麼（哪一頁、哪一句、為什麼）、新增了哪些檢索測試、沒解決的問題。

作者回報「來源太長」時，告訴使用者：這份來源很長，一次讀完再寫品質會下降，建議按章節拆成幾個檔案再放進 `raw/`。由使用者決定要拆檔，還是照原樣處理。

### 檢查者的步驟

1. 一次檢查一頁。讀 `wiki/<頁面代號>.md`。
2. 對這一頁 `sources` 的每一筆，執行 `kb resolve <來源引用>`，讀它指到的原文。
3. 找這三種問題：
   - 頁面寫的內容，在引用的原文裡找不到依據。
   - 頁面寫的數值、名稱、步驟順序與原文不一致。
   - 來源引用指到的位置與頁面內容無關。
4. 有問題就直接修改頁面：刪掉沒有依據的內容，把不一致的地方改成與原文相同，把引用改到正確的位置。**只能依原文修正，不要補充原文沒有的內容。**
5. 全部頁面檢查完，有修改就執行 `kb commit "檢查 <來源檔>：<一句話說明修正了什麼>"`。沒有修改就不用 commit。
6. 為這份來源最重要的一到兩頁各加一題檢索測試，關鍵字用使用者實際會問的詞：

   ```
   kb test add --terms "<關鍵字>,<關鍵字>" --expect <頁面代號> --rank 3
   ```

   說這題現在不會通過時，在該頁的 `keywords` 或 `aliases` 補上關鍵字，執行 `kb commit "補關鍵字"`，再加一次。

## 處理一份來源的步驟（ingest）

這是作者做的事。一次處理一份來源。在知識庫資料夾內執行。

1. 執行 `kb ingest start`，看有哪些來源待處理。
2. 執行 `kb ingest start <來源檔>`，例如 `kb ingest start raw/spec.md`。
   輸出包含：要做的事、相關的既有頁面、頁面範本、來源內容。
3. 輸出說來源有很多段時，用 `kb ingest part 2`、`kb ingest part 3` … 讀完全部。
4. 在 `wiki/<分類>/<名稱>.md` 新增或修改頁面，照範本寫。
5. 執行 `kb ingest commit`。
   - 出現 `[錯誤]`：照每一項的「正確寫法」修改檔案，再執行 `kb ingest commit`。重複到通過。
   - 出現「ingest 完成」：這份來源處理完了。輸出會列出下一份待處理的來源。
6. 你是作者時到這裡結束，照任務訊息的格式回報。沒有派工者、自己依序處理時，還有待處理的來源就回到步驟 2。

來源檔是 PDF、Word、Excel、PowerPoint 時不能直接處理，`kb ingest start` 會擋下。請使用者先轉成 markdown。

來源帶圖片時（轉檔後的 `.md` 加一個圖片資料夾），使用者把整包放進 `raw/` 即可。`kb ingest start` 會自動把圖片搬到 `assets/`，並改好來源裡的圖片路徑。你不用搬圖片，也不用改路徑：頁面要放圖時，照來源內容裡的 `assets/…` 路徑原樣複製，並寫上說明文字。

### 來源有新版時

`kb ingest start` 把來源列為「內容有更新」時，執行 `kb ingest start <來源檔>`。輸出開頭是「開始更新來源」的話，這次只處理變動的部分：

1. 讀「來源的變更」。`-` 是舊版拿掉的行，`+` 是新版加入的行。
2. 「需要檢查的頁面」一頁一頁處理。打開 `wiki/<頁面代號>.md`，對照變更：
   - 內容過時了，或引用的位置不對：修改檔案。
   - 確定不用改：執行 `kb ingest keep <頁面代號>`。
3. 「新增的內容」值得記錄時，新增頁面，或補進既有頁面並在 sources 加上引用。
4. 執行 `kb ingest commit`。有頁面沒處理會被擋下，訊息會列出是哪幾頁。

「已自動調整行數的頁面」與「沒有受影響的頁面」不用處理，行數已經由 `kb` 改好了。
輸出開頭是「開始處理來源」的話，代表改動太大，照一般的 ingest 流程整份重新處理。

想放棄目前這一份、把頁面還原：`kb ingest abort`。
忘記做到哪裡：`kb ingest status`。

## 修改既有頁面（與新來源無關）

修錯字、補關鍵字、修檢查找到的問題時使用。

1. 直接修改 `wiki/` 裡的頁面。
2. 執行 `kb commit "一句話說明改了什麼"`。有 `[錯誤]` 就照訊息修正再執行一次。

## 檢查知識庫（lint）

1. 執行 `kb lint`。
2. `[錯誤]` 一定要處理，`[警告]` 逐項判斷。每一項都有「正確寫法」與「下一步」，照著做。
3. 修改了頁面就執行 `kb commit "修正 lint 問題"`。
4. 再執行一次 `kb lint` 確認。

### 內容檢查（使用者要求時才做）

`kb lint` 檢查不了內容對不對。使用者要求檢查內容時：

1. 讀 `index.md`，一次挑一個分類。
2. 讀該分類的每一頁，找這兩種問題：
   - 兩頁對同一件事的說法互相矛盾。
   - 頁面內容與它 `sources` 指到的來源原文不一致。
3. 把找到的問題列給使用者看，說明是哪兩頁、哪一句。**先不要改**，等使用者決定。
4. 使用者同意後修改頁面，執行 `kb commit "說明"`。

## 檢索測試

檢索測試確認「用某些關鍵字搜尋時，某一頁排在前幾名」。每次 commit 前會自動執行。

- `kb test`：執行全部測試。
- `kb test add --terms "鮑率,baud rate" --expect uart/baud-rate --rank 3`：新增一題。為重要的頁面各加一題，關鍵字用使用者實際會問的詞。
- `kb test remove <題號>`：頁面被刪除或改名、題目不再適用時移除。

測試沒過時，在預期頁面的 `keywords` 或 `aliases` 補上關鍵字。不要為了通過而移除還適用的題目。

## 撤銷

- `kb undo`：撤銷最近一次 ingest 或 commit。來源檔會留在 `raw/`，可以重新處理。
- 只在使用者要求時執行。

## 共享知識庫

知識庫可以放到共享資料夾讓其他人使用。只在使用者要求時執行這些指令。

- **開始作業前**：`kb pull`，取得別人推送的變更。
- **作業完成後**：`kb push`，其他人才看得到。`kb ingest commit` 的輸出會提醒還有幾筆沒推送。
- 第一次共享：向使用者問共享資料夾的路徑，執行 `kb share <共享資料夾路徑>/<知識庫代號>.git`。
- 取得別人已共享的知識庫來維護：`kb clone <共享路徑> <本機資料夾>`。

`kb pull` 說「本機與共享位置各自有新的變更」時，把訊息原文轉告使用者，等使用者決定，不要自己處理。

## 其他指令

- `kb check`：只檢查格式，比 `kb lint` 快。
- `kb validate wiki/<分類>/<名稱>.md`：只檢查一頁。
- `kb search <關鍵字>`：確認頁面搜尋得到。
- `kb search --grep "<樣式>" --scope raw`：用 regex 在來源檔裡找函式名、位址、錯誤碼出現在哪幾行。去掉 `--scope raw` 則是找頁面。
- `kb rebuild`：重新產生 `index.md` 與搜尋索引。`kb check` 說索引過期時使用。
